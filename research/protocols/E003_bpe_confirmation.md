# E003 — подтверждение выбранной пары на 8k BPE

Статус: зарегистрирован после E002 и до загрузки/токенизации большого FineWeb-шарда. E003 состоит из симметричной LR-калибровки baseline и сравнения двух выбранных методов. Validation используется для решений; test остаётся закрытым.

## Вопрос

Переносится ли наблюдавшийся в E002 компромисс auxiliary anytime-training на постановку задания: vocabulary 8192, context 512, модель 9.44M и новые seed? В частности, улучшает ли кандидат качество при T=16 или устойчивость при T=32 без ухудшения основной метрики?

## Данные и tokenizer

- `HuggingFaceFW/fineweb`, конфигурация `sample-10BT`.
- Один файл `sample/10BT/000_00000.parquet` на ревизии `9bb295ddab0e05d785b879661af7260fed5140fc`.
- Ожидаемый SHA-256 исходного файла: `6b552ea48424648dc86d00df276f93fdfc55e9ad342ce3e4affc23a3a370792b`.
- Exact whitespace-normalized duplicate является единой split-группой. Split определяется хешем полного нормализованного текста: 90% train, 5% validation, 5% test.
- Byte-level BPE vocabulary 8192 обучается только на первых 50,000 уникальных train-документах. EOS разделяет документы. Один tokenizer и один корпус используются всеми вариантами.
- Подготовить не меньше 110M train-токенов, 4M validation и 4M закрытых test-токенов. Основной eval — детерминированная выборка 2,048 непересекающих границы документа окон, то есть 1,048,576 target-токенов.

## Общая модель и обучение

Оба варианта используют width 512, intermediate 1280, 8 query heads, 2 KV heads, два общих блока, tied embeddings/head, relative input injection, FP16 GradScaler, AdamW `(β1=0.9, β2=0.95, wd=0.1)`, batch 64, context 512 и gradient checkpointing. Уникальных параметров должно быть не больше 10M; ожидается 9,440,513.

LR использует 2% warmup и cosine decay до 0.1× на горизонте 100M. Checkpoint на 25M является остановкой внутри этого расписания, поэтому его можно честно продолжить до 100M.

## Фаза A: симметричная LR-калибровка

Baseline `relative_fixed16`, seed 101, два независимых запуска по 5M токенов: peak LR `1e-3` и `2e-3`. У обоих зарегистрирован горизонт schedule 100M. Выбирается меньший validation NLL@16; при абсолютной разнице меньше 0.02 выбирается `1e-3` как более консервативный. Кандидат не получает отдельного поиска LR.

Эта фаза настраивает общий optimizer recipe и не входит в подтверждающую оценку эффекта метода.

## Фаза B: сравнение

Новые seed 23 и 47, по две траектории на seed:

| Вариант | Depth-RoPE | Training depth | Auxiliary loss |
| --- | --- | --- | --- |
| `relative_fixed16` | нет | 16 | нет |
| `combined_random8_16_aux` | да | uniform integer 8…16 | readout на `floor(T/2)`, вес 0.3→0 по горизонту 100M |

Первый checkpoint — 25M предъявленных target-токенов. Порядок non-overlapping train-окон согласован внутри seed между вариантами. Оценка: NLL/PPL при T=1/2/4/8/12/16/24/32/48/64, paired bootstrap по validation-документам, training time, peak memory и skipped updates.

## Зарегистрированное решение

Основная метрика — NLL@16. Метрика полезной глубины — `NLL@32−NLL@16`; минимум по сетке сообщается отдельно и не подменяет основную метрику.

Продолжать обе стороны до 100M только если на обоих seed выполняется одно из условий:

1. кандидат улучшает NLL@16 минимум на 0.02 и не ухудшает `Δ16→32`; или
2. кандидат улучшает `Δ16→32` минимум на 0.02, а NLL@16 ухудшается не более чем на 0.02.

Если знак эффекта расходится между seed либо порог не достигнут, E003 сохраняется как отрицательное подтверждение на 25M. Нельзя продолжить только понравившийся вариант. Test не открывается до фиксации метода, checkpoint и inference depth.

## Условия недействительности

Запуск не входит в сравнение при несовпадающих tokenizer/data hashes, превышении 10M параметров или 100M токенов на траекторию, повторении train-окон до 100M, non-finite loss, несовместимом resume или открытии test до решения. Технический smoke допускается на отдельном игрушечном корпусе и не считается языковым результатом.
